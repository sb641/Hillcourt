# 0201. `action` в записи сценария — имя приказа, а не его рычаг

## Назначение

Развести два смысла, которые делили один ключ `action`, и запретить их смешение
навсегда. Ключ рычага приказа `assign_work` — `work`.

Наследует ADR 0196 (приказ `assign_work` написан), ADR 0155 (закон не в силе без
проверки, падающей без механики), ADR 0174 (номера реестра уникальны). Старые
ADR не редактируются.

## Контекст

Стол плейтеста перебрал все 18 приказов игрока на живом прогоне. Четыре
оказались сломаны по неисправности, а не по закону. Этот ADR — про первую.

`runner.py::_dispatch_assign_work` читал `entry["action"]` и передавал это в
`assign_work` как **имя дела двора**:

```python
assign_work(world, str(entry["household"]), str(entry["action"]), ...)
```

А `_apply_script_entry` (`runner.py:322`) читает `str(entry.get("action"))` как
**имя приказа** и ищет его в `ACTION_HANDLERS`. Один ключ — два смысла: и
«приказ `assign_work`», и «дело `assign_work`».

Замер (воспроизведён мной до правки, `start_stand`, сид 1729):

```
{at_month: 1, action: assign_work, household: hh_family_01, work: work_plot}
→ ValueError: Неизвестное дело двора 'assign_work'
```

**Проверка была зелёной на сломанном приказе.** `test_player_orders.py:101`
утверждала `assertIn("assign_work", ACTION_HANDLERS)` — то есть присутствие имени
в таблице, а не достижимость кнопки. Это дословно случай ADR 0155: «тест зелёный,
потому что он ничего не проверяет». Приказ был в таблице и не мог быть нажат.

Сила механики, ради которой приказ и писался (ADR 0196), игроку была недоступна:
подача падает, дворы перестают голодать — и нажать это было нельзя.

## Решение

### 1. `action` — имя приказа, и только оно

`action` в записи `script:` означает **имя приказа** и ничего больше. Это следует
уже из устройства `_apply_script_entry` (поиск в `ACTION_HANDLERS`) и теперь
закреплено явно: `ACTION_HANDLERS` — единственный словарь, где `action` значит
имя приказа.

### 2. Рычаг приказа `assign_work` — ключ `work`

```yaml
- {at_month: 1, action: assign_work, household: hh_family_01, work: work_plot}
```

`work`, а не `main`, потому что `main` — имя поля в записи лога
(`player_actions`), где оно значит «главное дело, **к которому приказ привёл**».
Смешивать их нельзя: игрок, читающий лог, должен видеть в `main` результат
приказа, а не то, что он и так написал в `action`.

Мелкое дело — по-прежнему ключ `minor` (ADR 0196).

### 3. Обратная совместимость: `main` принимается, расхождение — отказ

Исторического имени `work` в репозитории не было (замер: `assign_work` не
встречается ни в одном `design/scenarios/*.yml`), но фикстуры могли писать
`main`. Он принимается **только** когда `work` нет. Если записаны оба и значения
разошлись — `ValueError` с обоими именами, а не «поберил любой из двух».

Это ровно тот закон, что уже действует для ключа месяца (`_target_month`,
ADR 0155-era: `month` ≠ `at_month` — отказ, а не выбор любого). Один канонический
имя, историческое принимается, расхождение называется.

### 4. Нет рычага — внятный отказ, а не «неизвестное дело»

Раньше запись без дела падала `ValueError: Неизвестное дело двора 'assign_work'`
— сообщение вводило в заблуждение, потому что дело в записи **было**, просто
читалось не оттуда. Теперь отказ называет ключ (`work`), объясняет, что `action`
означает имя приказа, и печатает верный пример записи.

### 5. Проверка формы записи отделена от отказа закона

Проверка «есть ли `work`» выполняется в `_check_entry_shape` **до** `try`
(`ENTRY_SHAPE_CHECKS`). Это граница из ADR 0202: опечатка автора сценария обязана
ронять прогон, а не превращаться в «лорд не смог назначить работу». Подробности
границы — ADR 0202.

## Альтернативы

- **Оставить `action` и для приказа, и для дела.** Отвергнуто замером: это и есть
  дыра. Один ключ с двумя смыслами нельзя разрешить без разбора контекста, а
  контекста (`какое поле заполнено`) у приказа нет.
- **Переименовать приказ, а не рычаг** (например, `lord_assign_work`, а `action`
  оставить делом). Отвергнуто: сломаны все 18 приказов сразу и все сценарии, ради
  одного. Имя приказа — это то, что пишут в `ACTION_HANDLERS`, менять его
  дороже, чем добавить ключ.
- **Убрать `assign_work` из таблицы приказов, раз он не работал.** Отвергнуто:
  механика рабочая и нужная (ADR 0196), сломана была обвязка сценария.
- **Молча подставлять `work_plot`, когда `work` нет.** Отвергнуто прямо: это
  «поберил любой из двух» в новой одежде, то есть ровно тот брак, который
  `_target_month` запрещает для месяца. Молчаливая подстановка сделала бы
  опечатку неотличимой от замысла.

## Последствия

- **Кнопка нажимается.** Замер после правки: запись с `work` назначает двору
  дело, и мир меняется — подача сеньору за 12 месяцев `start_stand` падает
  37.02 → 33.00 (приказ) против 37.02 (без приказа), сид 1729.
- **Фиктивная проверка заменена настоящей.** `assertIn(имя, ACTION_HANDLERS)`
  удалена; вместо неё путь игрока целиком: запись сценария → `_apply_script_entry`
  → двор получил дело → мир изменился. Проверено мутацией: возврат
  `str(entry["action"])` роняет **2 теста** из 22.
- **Ни один сценарий не сломан.** Замер: `assign_work` не встречается ни в одном
  `design/scenarios/*.yml`, то есть правка ничего не переписывает молча.


## Что запрещено следующим агентам

- **Не читать `entry["action"]` как рычаг в обработчике приказа.** `action` —
  имя приказа. Рычаг — отдельный ключ с названием в `AGENTS.md` §1.
- **Не проверять приказ через `assertIn(имя, ACTION_HANDLERS)`.** Это проверка
  присутствия, а не достижимости, и она была зелёной на сломанном приказе
  (ADR 0155). Проверка обязана проходить путь игрока: запись сценария →
  `_apply_script_entry` → изменение мира.
- **Не «поберять любой из двух» рычагов.** `work` и `main` одновременно с разными
  значениями — отказ с обоими именами.
- **Не объявлять приказ сломанным, не проверив его через запись сценария.**
  Прямой вызов функции обходит ровно тот слой, где был баг.
